# ElderMoodAI 项目章程

**英文名**: ElderMoodAI
**中文名**: 居家老人情感分析及可视化系统

## 核心原则

### I. 隐私优先

本系统处理居家老人的情感状态等敏感个人数据，隐私保护是所有设计与实现决策的最高优先级。
具体要求：

- 所有个人数据（包括情感分析结果、生物特征信号、行为数据）MUST 在本地或受控环境中处理，禁止未经授权传输至第三方云端服务。
- 数据采集 MUST 遵循最小必要原则：仅采集完成功能所必需的数据，不得过度采集。
- 用户数据 MUST 在存储和传输过程中加密；静态数据加密算法不低于 AES-256，传输层 MUST 使用 TLS 1.2 及以上。
- 数据保留期限 MUST 在规范中明确定义；超期数据 MUST 自动清除或提供手动清除机制。
- 任何涉及个人数据的功能变更 MUST 经过隐私影响评估（Privacy Impact Assessment）后方可实施。

**理由**: 老年用户群体属于弱势群体，其情感与健康数据一旦泄露将造成严重的个人伤害和法律风险。

### II. 身份权限分层（最小权限原则）

系统 MUST 实现明确的多层级身份与权限体系，各层级之间不可越权访问。

- 权限层级 MUST 在规范阶段明确定义（例如：总管理员、家庭成员、护理人员、只读观察者等），并在实现中严格执行。
- 每个角色 MUST 只能访问其职责范围内的数据和功能；跨层级访问 MUST 被系统拒绝并记录日志。
- 权限变更（角色分配、权限升降）MUST 由总管理员执行，并留有审计日志。
- 认证机制 MUST 对所有非公开接口强制执行；禁止存在未受保护的管理端点。
- 权限模型变更属于破坏性变更，MUST 触发章程 MAJOR 版本递增并制定迁移计划。

**理由**: 居家老人数据涉及多方关系人（家属、护理人员、医疗机构），明确的权限边界是防止数据滥用的核心机制。

### III. 测试优先（不可协商）

所有功能实现 MUST 遵循测试驱动开发（TDD）流程：先编写测试 → 确认测试失败 → 实现功能 → 确认测试通过。

- 涉及隐私数据处理、权限校验、情感分析核心逻辑的代码 MUST 有单元测试覆盖。
- 新功能合并前 MUST 通过所有现有测试；禁止在测试失败状态下合并代码。
- 测试覆盖率目标：核心业务逻辑 SHOULD 达到 80% 以上行覆盖率。

**理由**: 情感分析结果直接影响对老人状态的判断，错误的分析结果可能导致错误的护理决策，测试是保障系统可靠性的基础。

### IV. 集成测试

以下场景 MUST 编写集成测试：

- 新模块或服务的对外契约（API 契约测试）。
- 权限层级之间的访问控制边界（越权尝试 MUST 被测试覆盖）。
- 情感分析结果的端到端数据流（从数据采集到可视化输出）。
- 外部依赖（数据库、第三方 AI 服务）的集成点，MUST 包含故障模拟测试。

**理由**: 居家老人系统的各组件（采集、分析、存储、可视化）高度耦合，集成测试是发现跨组件问题的必要手段。

### V. 简单性（YAGNI 原则）

从最简单的可行方案开始；复杂性 MUST 有明确的业务需求驱动，不得为"将来可能需要"而提前引入。

- 每个新增的抽象层、设计模式或第三方依赖 MUST 在实施计划中说明其必要性。
- 当存在更简单的替代方案时，MUST 优先选择简单方案，除非有可量化的理由证明复杂方案的必要性。
- 代码复杂度增加（例如：新增服务、新增数据库、新增外部依赖）MUST 记录在实施计划的"复杂度跟踪"表中。

**理由**: 面向老年用户的系统需要长期维护，过度设计会增加维护成本并引入不必要的故障点。

## 安全与合规

- 所有用户输入 MUST 经过验证和清洗，防止注入攻击（SQL 注入、XSS 等）。
- 敏感配置（密钥、数据库凭证、API Token）MUST 通过环境变量或密钥管理服务注入，禁止硬编码在代码库中。
- 安全漏洞修复 MUST 优先于功能开发，严重漏洞（CVSS ≥ 7.0）MUST 在 48 小时内制定修复计划。
- 系统 SHOULD 记录所有数据访问操作的审计日志，日志 MUST 不可篡改且保留不少于 90 天。
- 如项目未来涉及医疗数据，MUST 在规范阶段评估适用的合规要求（如 HIPAA、GDPR 或中国《个人信息保护法》）。

## 开发工作流程

- 所有功能开发 MUST 基于功能分支进行，禁止直接向主分支提交代码。
- 代码合并 MUST 经过代码审查；涉及隐私数据处理或权限逻辑的变更 MUST 由总管理员审查批准。
- 每个功能 MUST 有对应的规范文件（spec.md）和实施计划（plan.md）后方可开始实现。
- 实施计划 MUST 通过章程检查门控后方可进入开发阶段。
- 发布前 MUST 运行完整测试套件并确认全部通过。

## 治理

本章程是所有开发决策的最高权威文件，优先于其他实践文档和个人偏好。

**修正程序**:

- 章程修正由**总管理员（单一负责人）**决定并执行。
- 每次修正 MUST 更新版本号（遵循语义版本控制）、`LAST_AMENDED_DATE`，并在同步影响报告中记录变更内容。
- 破坏性变更（删除或重新定义原则、权限模型变更）MUST 同时提供迁移计划。

**版本控制策略**:

- MAJOR：向后不兼容的治理变更（原则删除、重新定义、权限模型破坏性变更）。
- MINOR：新增原则、新增章节、实质性扩展现有指导。
- PATCH：措辞澄清、拼写修正、非语义优化。

**合规审查**:

- 每个功能的实施计划 MUST 包含章程检查部分，验证与所有原则的符合性。
- 章程合规性 MUST 在代码审查阶段验证；违规项 MUST 在合并前解决。
